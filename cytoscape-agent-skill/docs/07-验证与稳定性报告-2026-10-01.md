## 2. 验证方法与证据

### 2.1 确定性 —— 用户最关心的那条

要求是「结果与原始项目一模一样，不允许因 AI 或数据变化」。可验证的形式是：
**同一份输入 + 同一版本引擎 → 同一份字节输出**。

实测（`galFiltered.sif` 导入 → 导出 SIF）：

| 次 | 方式 | sha256 | 字节 |
|---|---|---|---|
| 1 | 手工两条命令 | `eaf6a4b2…4c58d` | 7181 |
| 2 | 手工两条命令（重新执行） | `eaf6a4b2…4c58d` | 7181 |
| 3 | `cyctl run` 工作流 | `eaf6a4b2…4c58d` | 7181 |

三次完全一致。基线文件已存入 `evidence/baseline-galFiltered-export-cytoscape-3.10.5.sif`，
任何人可在同版本引擎上重跑比对。

规模核对：导入后网络 **330 节点 / 359 边**，两次独立导入完全一致。
该断言已固化为用例 `TestLiveEngine.test_import_sample_network_gives_expected_counts`
与 `test_reimport_of_same_file_gives_identical_counts`。

> **边界（必须说清）**：随机性来自力导向类布局的节点坐标。Cytoscape 每次运行
> `layout force-directed` 得到的坐标不同，两次导出 SIF **坐标系**可能不同。
> 可复现的是**拓扑、属性与表数据**，不是节点坐标。见 `docs/02` §2.1。
> 本报告的确定性结论只覆盖拓扑与表数据。

## 3. 本轮发现并修复的问题

全部是实测暴露的，不是代码审查的推测。

### 3.1 【严重】`cyctl commands command quit` 会真的把引擎关掉

**现象**：查询命令帮助时，`command quit` 被实际执行，引擎关闭。
**根因**：CyREST 的语义是「`GET /commands/{ns}/{cmd}` **即执行该命令**」——
对**不需要参数**的命令，这个请求就是执行；只有需要参数的命令才返回参数清单。
**连带后果**：GUI 模式下 `quit` 触发 FelixShutdown 关闭了 CyREST，
但 JVM 卡在「退出确认对话框」上不退出 —— 实测留下一个 **1.3 GB 的僵尸进程**，
而端口 1234 已经关闭。表现成「没有进程在监听，却还有进程吃内存」，极难定位。
**修复**：
- `quit` / `exit` / `shutdown` / `halt` 类命令**永久拒绝**（`--allow-execute` 也不放行）；
- 其余命令默认走**只读**路径（列命名空间清单，确认存在性），要看参数清单须显式 `--allow-execute`；
- 输出新增 `executed` / `source` 字段，调用方一眼能看出走的是哪条路径；
- 关引擎引导用 `cyctl stop`（以「端口已关闭」为唯一成功判据，能清理残留进程）。
**用例**：`TestCommandsGuard` 4 条（含「危险命令在发请求之前就被拦下」——用死端口证明）。

### 3.2 【严重】空命令以退出码 1 结束，违反输出契约

**现象**：`cyctl cmd ""` 与 `cyctl cmd "   "` 返回退出码 **1**。
**根因**：`split_command` 抛的 `ValueError` 没被 `cmd` 子命令捕获，一路落到 `main` 的兜底分支。
**影响**：输出契约规定退出码只能是 `0/2/3/4/5`。按契约解析的调用方遇到 `1` 会当成未知灾难。
（stdout 倒是有 JSON —— 这一点还好，但退出码错了就是错了。）
**修复**：归为**用法错误**（`2`），并在 `describe` 里保持契约表述一致。
**用例**：`TestHostileInputs.test_empty_command_is_usage_error_not_internal`（5 种空白输入）。

### 3.3 【能力缺失】`cyctl rest` 无法请求纯文本端点（HTTP 406）

**现象**：`cyctl rest GET commands` → HTTP 406。
**根因**：CyREST 的 help 类端点（`commands`、`commands/{ns}`）**只接受 `Accept: text/plain`**。
`cyrest_request` 本身支持 accept，但 `call_operation` 没有透传，CLI 也没有暴露开关。
**影响**：自带示例工作流的第一步就是 `rest GET commands` —— 整条工作流必然失败。
**修复**：`call_operation` 增加 `accept` 参数；`cyctl rest` 增加 `--accept`；
`cyctl run` 的步骤支持 `"accept"` 字段。
**用例**：`TestRunAndRestContract.test_rest_exposes_accept`。

### 3.4 【能力缺失】工作流相对路径解析到引擎安装目录

**现象**：工作流里写 `file="data/galFiltered.sif"`，导入失败。
**根因**：执行期真正读文件的是 **Cytoscape 引擎**，而引擎的 cwd 是它自己的安装目录
（`cyctl start` 以 `cwd=launcher 目录` 启动）。相对路径解析到不相干的位置，
报错信息里也看不出是路径问题。写死绝对路径又不可移植。
**修复**：
- `inputs` 的相对路径一律相对**工作流文件所在目录**解析；
- 命令字符串支持 `{workflow_dir}` / `{input_dir}` / `{input}` / `{input0}` 占位符；
- 溯源清单里记录**实际执行**的命令（占位符已展开），否则事后无法复原。
**用例**：`TestRunAndRestContract` 3 条。

### 3.5 【示例错误】示例工作流本身跑不通

- 第 1 步用了不存在的命令 `layout getLayoutNames`（真实命令是 `get preferred`）；
- 第 0 步缺 `accept: text/plain`。

两处都已修正，并补上自带示例数据 `data/galFiltered.sif`（6.8 KB，官方示例网络）。
`test_demo_workflow_is_valid_and_uses_placeholder` 锁定「示例必须合法且用占位符」。

### 3.6 顺带修正的 3 处测试缺陷（不是产品缺陷）

| 缺陷 | 为什么错 |
|---|---|
| `network list` 断言写死 `data.networks` 必存在 | 干净引擎一个网络都没有时，引擎返回 `{"data": {}}` —— 连键都没有。原断言在任何刚启动的引擎上都会误报 |
| 敌意输入用 `"x" * 200000` / `"a" * 100000` | 超出 Windows CreateProcess 命令行上限（约 32K），在**启动进程之前**就抛 WinError 206 —— 那是在测操作系统。真正的超长字符串处理改在进程内直接覆盖 |
| 敌意输入用 `"net\u0000work list"` | Windows 命令行**无法携带 NUL**，同样在启动前就失败，测不到 cyctl |

## 4. 稳定性测试覆盖面

`tests/test_stability.py` 六组，每组对应一个**实际发生过的**失败模式：

| 组 | 覆盖 | 关键点 |
|---|---|---|
| `TestProxyPolicy` | 下载网络路径决策 | `urllib.getproxies()` 会读 Windows 注册表 WinINET 设置，把用户从未配置的代理套上来。实测吞吐从 10.5 MB/s 掉到 180 KB/s（57 倍） |
| `TestConcurrentRequests` | 并发下响应不得串包 | 共享 `OpenerDirector` 若串包，Agent 并发下会拿到别人的结果 —— 在生信分析里等于结论错误，且完全静默 |
| `TestEngineVersionProbe` | 版本探测位置 | 版本在 `/v1/version`，**不在**根端点 `/v1/` |
| `TestIdempotency` | 重复执行语义 | 已安装不得重复下载；重复调用结果一致 |
| `TestResourceStability` | 长循环资源 | 150 次请求间句柄/内存不得持续增长（句柄数在本机不可读，该用例跳过） |
| `TestHostileInputs` | 任何输入不得破坏契约 | stdout 恒为一个 JSON 对象，退出码绝不出现 1（23 项敌意输入实测 0 问题） |
| `TestLiveEngine` | 真实引擎端到端 | 版本==锁定版本、同命令两次指纹相同、真实并发、导入规模、**MCP 协议往返** |

## 5. 诚实边界：本轮**没有**验证的部分

这一节比上面的结论更重要。以下都是**已知未覆盖**，不应被解读为「已通过」。

1. **只在 Windows x64 上实测过。** macOS / Linux 的启动、无头（Xvfb）路径只做了代码与
   单元测试层面的覆盖，没有在真机上跑过引擎。`versions.lock.json` 的平台矩阵来自官方
   发布页，但「能下载到」≠「已跑通」。
2. **九类宿主的 MCP 配置只验证了「写出的配置正确」**（字段名逐条对齐官方文档、有 49 个
   用例锁定），**没有在真实宿主客户端里连过一次**。也就是说：配置的**正确性**有依据，
   **可用性**未经端到端确认。
3. **system / attach 引擎模式未实测。** 本机没装 Cytoscape，这两条路径只有单元测试覆盖。
   用这两种模式时必须把**实际引擎版本**记进溯源清单，否则「结果一致」无从谈起。
4. **未做长时间（小时级）稳定性跑。** 资源稳定性用 150 次循环近似，不是长跑。
5. **随机性边界**：力导向类布局的节点坐标不可复现（引擎固有行为，非本工具引入）。
6. **未覆盖全部 Cytoscape 命令。** 验证走通了「导入 → 布局查询 → 导出」这条主链，
   但 Cypher/分析类命令的行为边界没有逐个验证。工具本身不实现算法，所以风险主要在
   「命令是否存在 / 参数名是否正确」—— 这靠 `cyctl commands` 查，不靠猜。

## 6. 打包

```
python tools/package.py --verify
```

产出 `dist/` 下：

- `cytoscape-agent-skill-0.3.3.zip`
- `cytoscape-agent-skill-0.3.3.tar.gz`
- `SHA256SUMS`

打包约定（每条都对应一个踩过的坑）：

- **排除 `runtime/`**（本机已 1.07 GB：引擎 370 MB + JRE + 下载缓存 + MCP jar）。
  打进包里既传不出去，也会让 `SHA256SUMS` 失去意义。
- **逐字节写入、固定时间戳**，保证同一个包每次打出来哈希相同（可复现）。
- 归档内容与源文件**逐字节比对**后才输出（自检）；同时拒绝任何 CRLF。
- `--verify` 会解压到临时目录并跑全量测试，确认包可独立运行。

## 7. 复现步骤

```bash
# 1. 环境体检
python scripts/cyctl.py doctor

# 2. 准备自带引擎（约 580 MB；本机实测 54 秒）

# 4. 确认版本与锁定值一致
python scripts/cyctl.py status

python -m unittest discover -s tests

python tools/mcp_e2e.py

# 7. 端到端工作流 + 溯源清单
python scripts/cyctl.py run workflows/demo.workflow.json --out runs/demo-manifest.json

# 8. 打包并校验
python tools/package.py --verify
```
